Case Study

Resolved

They have AI to deny your complaint. Now you have AI to fight back.

Resolved is a real, working prototype — view the repo. Two AI integrations (evidence extraction, letter drafting) run live against the Claude API; strategy selection, escalation, and the dashboard run on staged fallback data so the demo never breaks mid-pitch. Business impact figures below are reasoned estimates, not measured production numbers.

1. The Original Workflow

India has 250–350M+ online shoppers, and quick-commerce's 10–15 minute delivery promise generates complaints faster than anyone can review them. Today, resolving one means photographing the evidence, writing up what happened from memory, and dropping it into a vendor's support chat — which is increasingly a bot trained to stall, deflect, and quietly close the ticket before a human reads it.

If that fails — and it usually does — the consumer is on their own to figure out what's next. Almost nobody knows that the Consumer Protection Act 2019 exists, let alone which section applies to their case. The formal path (National Consumer Helpline → e-Daakhil → consumer court) is a maze of different portals, forms, and evidentiary requirements, slow enough that courts are sitting on a backlog of hundreds of thousands of cases, some taking years to close. Most people give up after the first bounced chat message.

3. Prerequisites

  1. Legible evidence. A blurry receipt photo or a screenshot with critical fields cropped out won't yield reliable extraction — the vision step has an honest floor on input quality.
  2. A maintained vendor-to-channel map. The system needs a current mapping of each vendor to its correct escalation channel and tone, since grievance contacts and complaint portals change over time.
  3. A letter specific enough to be trusted and sent as-is. If the draft reads as templated, users will over-edit it or not send it at all — the whole point is removing friction, not adding a review burden.

4. The AI-Enabled Redesign

  1. Extract — Claude's vision model reads a photo, screenshot, or forwarded email and pulls vendor, order ID, amount, issue, severity, and timestamp straight off the evidence. No forms, no formatting rules.
  2. Strategize — the system selects a vendor-specific play: the right channel, the right tone, and the exact clause of Indian consumer law to cite — e.g. Consumer Protection Act 2019 §2(11).
  3. Draft — a firm, law-cited complaint letter streams in live via the Claude API, ready to send or edit.
  4. Escalate — if ignored, the system climbs a five-step ladder on its own: vendor channel → public post → grievance officer → National Consumer Helpline → e-Daakhil consumer court.

5. Human Fallback Triggers

  • Low-confidence extraction (e.g. vendor name or amount not clearly legible) — routed to a manual-entry confirmation step before any letter is drafted, never auto-filled with a guess.
  • Any rung involving a formal legal filing (e-Daakhil consumer court) — requires explicit user confirmation before submission, since this creates a real legal record.
  • Issues that don't clearly map to a Consumer Protection Act violation (e.g. a subjective quality complaint with no clear breach) — flagged for the user to review the drafted legal basis themselves, rather than citing a clause that may not actually apply.
  • The public-post escalation step — always requires explicit per-case opt-in, never automatic, since a public post carries reputational and legal risk for the user too.

6. Sample AI Prompt

System prompt — evidence extractionYou are a consumer complaint evidence extraction assistant. You are given an image (photo, screenshot, or forwarded email) describing a consumer's problem with a purchase or service. Extract ONLY what is visibly present in the image: 1. vendor: the company name, if visible or clearly inferable from a logo/domain 2. order_id: any order/reference number visible 3. amount: the disputed amount, with currency 4. issue: a one-sentence factual description of the problem, using only what's shown (not what's implied) 5. severity: "minor" | "moderate" | "severe" based on amount, safety concern, and breach language present 6. timestamp: any date/time visible in the evidence If a field is not clearly visible or is ambiguous, output null for that field rather than guessing. Do not infer an order ID or amount from typical patterns — only report what is actually shown. Output strict JSON: { "vendor": string|null, "order_id": string|null, "amount": {"value": number, "currency": string}|null, "issue": string, "severity": "minor"|"moderate"|"severe", "timestamp": string|null, "confidence": "high"|"medium"|"low" }
Example input — a screenshot of an order confirmation ("Order #4471293, Total ₹2,450, Zomato") with a chat message below: "my order arrived cold and 40 minutes late, support said nothing they can do"[image: order confirmation + support chat screenshot]
Example output{ "vendor": "Zomato", "order_id": "4471293", "amount": { "value": 2450, "currency": "INR" }, "issue": "Order arrived cold and 40 minutes later than promised; vendor support declined to act.", "severity": "moderate", "timestamp": null, "confidence": "high" }

Error handling: if the image is unrelated to a consumer complaint (a random photo, a meme, an unrelated document), the model outputs all fields null, confidence: "low", and does not fabricate a plausible-sounding complaint just because one was expected.

The math, shown: if drafting and routing one complaint manually takes ~40 minutes and collapses to ~3 minutes of review, that's ~37 minutes saved per complaint — and a repeat-issue customer (a recurring late-delivery pattern, say) filing 3 complaints in a quarter saves roughly 110 minutes, without ever having to look up which law applies.

9. Product Thinking — Risks & Tradeoffs

Risk: an incorrectly cited law section could undermine an otherwise valid complaint's credibility. Mitigated by keeping the citation library narrow and reviewed rather than letting the model freely invent clause numbers — any citation the system's internal library doesn't recognize falls back to a letter that describes the issue plainly without a specific clause, rather than a confidently wrong one.

Risk: automated escalation without a human decision point could file something the user regrets — a public post or a formal court filing carries consequences a closed support ticket doesn't. Mitigated by the explicit opt-in fallback trigger in Section 5.

Design choice — what stays human, and why: deciding to escalate to a public post or a formal e-Daakhil filing always stays human. Extraction and drafting are the parts genuinely bottlenecked by manual effort; consequence-bearing decisions aren't the system's to make alone.

Dependency: quality is bounded by the vendor-escalation-channel map staying current. A stale mapping sends a complaint to a dead-end address, which is arguably worse than doing nothing, since it creates false confidence that the complaint is actually progressing.

10. Current State & What's Next

  • Live today: two real Claude API integrations — photo-to-facts extraction and complaint-letter drafting, both running against real evidence, not mocked data.
  • Staged for the demo: strategy selection, escalation, and the dashboard run on fallback data so the prototype never breaks mid-pitch — a deliberate build-order choice, not a gap nobody noticed.
  • Not built yet: no backend, auth, or persistence — state lives in React and resets on refresh. No real vendor or regulator integrations; filing, posting, and calling are simulated end states.
  • Next build, honestly: wiring the escalation ladder to real channels, starting with the two or three highest-volume e-commerce and food-delivery vendors, and persisting case state so a complaint survives a refresh.
